# Техническое задание: учебный проект для оператора SIM-карт

## 1. Цель проекта

Разработать учебный проект для демонстрации работы AI-агентов над backend/data-задачей: от анализа требований и проектирования базы данных до миграций, автоматизации и документации.

Проект моделирует компанию, которая продает SIM-карты физическим и юридическим лицам, принимает платежи, подключает услуги и ведет учебную базу знаний по услугам сотовой связи.

## 2. Ожидаемый результат

В результате должен получиться репозиторий с:

- SQL-схемой базы данных;
- миграциями для создания и изменения структуры БД;
- seed-данными для локального запуска;
- скриптами автоматизации;
- документацией по архитектуре, запуску и работе с данными;
- примерами запросов для проверки бизнес-сценариев.

## 3. Основные сущности

### Клиенты

Система должна поддерживать два типа клиентов:

- физические лица;
- юридические лица.

Для клиента необходимо хранить:

- уникальный идентификатор;
- тип клиента;
- имя или название компании;
- контактный телефон;
- email;
- дату регистрации;
- статус: active, blocked, archived.

Для физических лиц дополнительно:

- фамилию, имя, отчество;
- дату рождения;
- паспортные данные.

Для юридических лиц дополнительно:

- ИНН;
- КПП;
- юридический адрес;
- контактное лицо.

### SIM-карты

Для SIM-карты необходимо хранить:

- уникальный идентификатор;
- ICCID;
- номер телефона;
- текущий статус: available, reserved, active, blocked, lost;
- дату выпуска;
- дату активации;
- клиента-владельца;
- текущий тариф или набор подключенных услуг.

Одна SIM-карта может принадлежать только одному клиенту, но клиент может владеть несколькими SIM-картами.

### Услуги

Услуга описывает подключаемую возможность оператора:

- мобильный интернет;
- пакеты минут;
- SMS-пакеты;
- роуминг;
- статический IP;
- корпоративные опции.

Для услуги необходимо хранить:

- уникальный идентификатор;
- название;
- описание;
- тип услуги;
- стоимость;
- период списания;
- статус: active, deprecated, archived.

### Подключенные услуги

Система должна хранить связь SIM-карт с услугами:

- SIM-карта;
- услуга;
- дата подключения;
- дата отключения;
- статус подключения;
- цена на момент подключения.

### Платежи

Платежи должны быть связаны с клиентом и, при необходимости, с конкретной SIM-картой.

Для платежа необходимо хранить:

- уникальный идентификатор;
- клиента;
- SIM-карту, если платеж относится к конкретному номеру;
- сумму;
- валюту;
- способ оплаты;
- статус: pending, paid, failed, refunded;
- дату создания;
- дату подтверждения.

### Учебная база по услугам сотовой связи

База знаний должна содержать материалы для сотрудников или клиентов:

- статьи по услугам;
- инструкции по подключению;
- ответы на частые вопросы;
- ограничения и условия использования.

Для статьи необходимо хранить:

- уникальный идентификатор;
- заголовок;
- slug;
- категорию;
- содержимое;
- связанные услуги;
- статус публикации: draft, published, archived;
- дату создания;
- дату обновления.

## 4. Требования к базе данных

База данных должна быть спроектирована в реляционной модели.

Минимальный набор таблиц:

- `clients`;
- `individual_clients`;
- `legal_clients`;
- `sim_cards`;
- `services`;
- `sim_card_services`;
- `payments`;
- `knowledge_base_articles`;
- `article_services`;
- `migration_history`, если не используется готовый инструмент миграций.

Обязательные требования:

- использовать первичные и внешние ключи;
- добавить уникальные ограничения для ICCID, номера телефона, email, ИНН и slug;
- добавить проверки для статусов, сумм платежей и дат;
- предусмотреть индексы для частых запросов;
- не хранить чувствительные данные без явного комментария о рисках;
- оформить SQL-схему отдельным файлом.

## 5. Миграции

Проект должен содержать миграции, которые можно применить на пустую базу.

Минимальный набор:

- создание базовых таблиц;
- добавление индексов и ограничений;
- добавление тестовых справочников услуг;
- пример изменения схемы, например добавление нового статуса или поля.

Миграции должны быть упорядочены по номеру или timestamp.

## 6. Seed-данные

Seed-скрипт должен добавлять:

- несколько физических лиц;
- несколько юридических лиц;
- набор SIM-карт в разных статусах;
- список услуг;
- подключенные услуги;
- платежи с разными статусами;
- статьи базы знаний.

Данные должны быть вымышленными.

## 7. Скрипты автоматизации

В проекте должны быть команды или shell-скрипты для:

- создания локальной базы данных;
- применения миграций;
- отката последней миграции, если выбранный инструмент это поддерживает;
- заполнения базы seed-данными;
- сброса локальной базы;
- запуска SQL-проверок или smoke-тестов.

Пример ожидаемых команд:

```bash
make db-create
make db-migrate
make db-seed
make db-reset
make db-check
```

## 8. Документация

Проект должен содержать документацию:

- `README.md` — что делает проект и как его запустить;
- `docs/architecture.md` — описание модели данных и ключевых решений;
- `docs/database.md` — таблицы, связи, индексы, ограничения;
- `docs/commands.md` — список команд автоматизации;
- `docs/agent-workflow.md` — как агенты должны работать над проектом;
- `docs/examples.md` — примеры SQL-запросов.

## 9. Примеры бизнес-сценариев

Система должна позволять выполнить SQL-запросы для сценариев:

- найти все активные SIM-карты клиента;
- посмотреть услуги, подключенные к конкретной SIM-карте;
- посчитать сумму платежей клиента за период;
- найти клиентов с неоплаченными платежами;
- вывести опубликованные статьи по конкретной услуге;
- найти SIM-карты без активных услуг;
- проверить, какие юридические лица имеют больше 10 SIM-карт.

## 10. Нефункциональные требования

- Схема должна быть понятной для учебного разбора.
- Названия таблиц и колонок должны быть единообразными.
- SQL должен быть читаемым и форматированным.
- Проект должен запускаться локально без внешних платных сервисов.
- Все команды должны быть описаны в документации.
- Решения, принятые агентами, должны фиксироваться в отдельном логе или документации.

## 11. Критерии приемки

Проект считается готовым, если:

- база создается с нуля одной командой;
- все миграции применяются без ошибок;
- seed-данные загружаются повторяемо;
- внешние ключи и ограничения работают;
- есть минимум 7 примеров SQL-запросов;
- документация объясняет структуру проекта и запуск;
- агент может по этому ТЗ разбить работу на план, реализовать схему, написать миграции и провести проверку.

## 12. Ограничения

- Это учебный проект, не production-система.
- Авторизация, личный кабинет и UI не входят в обязательный объем.
- Интеграция с реальными платежными системами не требуется.
- Паспортные данные и другие чувствительные поля используются только как пример модели данных.
