# Тарифы и абонплата

> Дата: 2026-07-15 · Проект: deepcoding-guides · Обновлено: 2026-07-15

## Цель

Добавить в учебный проект Telecom SIM Cards тарифы и помесячную абонплату: таблицы `tariffs`, `tariff_services`, `charges`, nullable-привязку тарифа к SIM-карте, идемпотентное начисление, проверку целостности и отчёт по начисленной выручке.

Работа велась по схеме brainstorming → design spec → implementation plan → реализация отдельными субагентами → task-review после каждого этапа → итоговое ревью. Пользователь отдельно указал не создавать коммиты.

## Что сделано

### Согласование требований

- Выбрана простая модель без отдельной истории назначений тарифов: текущий `tariff_id` хранится в `sim_cards`, а прошлое состояние фиксируется снимками в `charges`.
- `sim_cards.tariff_id` оставлен nullable. Активную SIM без тарифа выявляет SQL-аудит, а не жёсткий constraint.
- Начисление выполняется один раз за календарный месяц без prorating. Повторный запуск подавляется через `UNIQUE (sim_card_id, billing_period)` и `INSERT OR IGNORE`.
- Отчёт считает начисленную абонплату из `charges`, а не фактически оплаченные `payments`.

## Ключевые решения

1. **Текущий тариф вместо истории назначений.** Отдельную таблицу истории отклонили как лишнюю для учебного объёма. Историческая достоверность начисления обеспечивается снимком `tariff_id`, `tariff_name` и `amount` в `charges`.
2. **Nullable `tariff_id`.** Неполные бизнес-данные разрешены схемой и выявляются аудитом. Это повторяет существующий подход `clients-without-type-details`.
3. **Неизменяемые финансовые строки.** UPDATE/DELETE `charges` запрещены триггерами, а удаление связанной SIM или тарифа блокируется `ON DELETE RESTRICT`.
4. **Архивирование не останавливает текущие начисления.** Триггер проверяет тариф только в момент назначения. В биллинге нет фильтра по `tariffs.status`.
5. **Начисленная, а не оплаченная выручка.** `charges` не связывается с `payments`; модель погашения задолженности в задачу не входит.
6. **Идемпотентность на уровне БД.** Повтор запуска безопасен независимо от CLI за счёт UNIQUE и `INSERT OR IGNORE`.
7. **Без коммитов и без worktree.** Пользователь выбрал работу в текущем каталоге `main` и попросил оставить изменения незакоммиченными.
8. **Тип клиента без снимка.** Для маленькой учебной доработки тип берётся у текущего владельца SIM. Поле в `charges` и миграция не добавлялись; смена владельца может изменить историческую разбивку отчёта.

## Вопросы и проблемы

Открытых блокеров нет.

Ограничение выбранной учебной модели: без истории статусов SIM и назначений тарифов команда не предназначена для точного перерасчёта далёких прошлых периодов. Она использует текущее состояние и сохраняет результат как снимок.

Отчёт по выручке также не хранит снимок типа клиента: историческая разбивка пересчитывается по текущему владельцу SIM.

Вспомогательный скрипт `.cursor/skills/sim-card-feature-workflow/scripts/run-checks.sh` устарел и вызывает отсутствующую цель `db-clean`. Проверки выполнены актуальными целями `db-reset` и `db-check`; сам skill-скрипт в этой сессии не менялся.
