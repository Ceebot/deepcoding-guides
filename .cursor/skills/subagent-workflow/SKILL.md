# Workflow субагентов (project/)

Цепочка для сложных задач: декомпозиция → реализация → тесты → ревью, с циклом до полного завершения.

## Когда применять

- крупная фича или целый блок задач из `todo.md`;
- рефакторинг или несколько связанных изменений в `project/`;
- задача, где важны и план, и тесты, и независимое ревью.

## Главное правило: каждый субагент — в своём контексте

**Нельзя** смешивать роли planner, worker, tester, reviewer в одном контексте основного чата.
**Нужно:** запускать каждого субагента отдельным вызовом, передавать роль из `.cursor/agents/<роль>.md`
и явный handoff в промпте. Родитель-оркестратор читает результат и только потом запускает следующего.

| Этап | Субагент | Артефакт |
|------|----------|----------|
| План | `planner` | файл плана в `.cursor/plans/` |
| Реализация | `worker` | правки в `project/`, тесты, запись в `task_logs.md` |
| Тесты | `tester` | новые/недостающие тесты, результат прогона |
| Ревью | `reviewer` | текст замечаний или «ок» |

## Последовательность

```
Задача → planner → worker → tester → reviewer → [замечания?] → worker (цикл) | завершено
```

1. **planner** — читает ТЗ/`todo.md`, декомпозирует, сохраняет план в `.cursor/plans/`. Код не трогает.
2. **worker** — реализует план по шагам в `project/`, пишет тесты, гоняет `make db-reset` и `make test`, выполняет skill `update-task-log`. Сообщает список изменённых файлов.
3. **tester** — добавляет недостающие тесты и краевые случаи, прогоняет `make test`.
4. **reviewer** — родитель сначала делает `git diff` и передаёт его reviewer вместе с планом и списком файлов. Reviewer только ищет проблемы, код не меняет.

## Цикл до завершения

| Исход ревью | Действие |
|-------------|----------|
| Есть замечания | Передать блок замечаний worker → worker правит → снова tester/reviewer |
| Замечаний нет | Задача завершена |

Цикл повторяется, пока reviewer не скажет «замечаний нет». Это и есть ценность связки: задача
доводится до конца автоматически, а не бросается на первом проходе.

## Протокол handoff

Субагенты стартуют с пустым контекстом — родитель явно передаёт всё нужное в промпте:
путь к плану, список изменённых файлов, вывод `git diff`, блок замечаний.

## Чеклист

- [ ] planner, worker, tester, reviewer запускались каждый в своём контексте;
- [ ] planner создал план в `.cursor/plans/`;
- [ ] worker реализовал шаги, отметил их в плане, обновил `task_logs.md`;
- [ ] tester прогнал `make test` — зелено;
- [ ] reviewer одобрил (замечаний нет);
- [ ] задача завершена.
