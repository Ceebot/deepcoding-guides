# Этап 14. Harness Engineering

[← К roadmap](../README.md)

Цель: дать имя всему, что мы строили вокруг агента с четвёртого этапа, и достроить два недостающих механизма — **гарантии, которые нельзя уговорить**, и **петлю обратной связи**, по которой агент видит результат своих действий.

## Агент = модель + harness

Модель — это «мозг». Всё остальное — системный промпт, инструменты, память, права, проверки, окружение — называется **harness** («обвязка»). Формула, которая закрепила термин в 2026 году, звучит так:

> Agent = Model + Harness. If you're not the model, you're the harness.
> — Vivek Trivedy, [The Anatomy of an Agent Harness](https://www.langchain.com/blog/the-anatomy-of-an-agent-harness), LangChain, март 2026

Саймон Виллисон определяет кодинг-агента ровно через это слово: это «software that acts as a harness for an LLM» — программа, которая служит обвязкой для модели и расширяет её невидимыми промптами и вызываемыми инструментами.

Аналогия из нашего мира. СУБД — это не только оптимизатор запросов. Вокруг него журнал транзакций, планировщик, права доступа, бэкапы, мониторинг. Оптимизатор в новой мажорной версии перепишут — обвязка останется, и именно она определяет, можно ли доверить базе прод. С агентом так же: **модель обновляется каждые несколько месяцев, harness остаётся вашим**.

## У нас уже есть harness — просто не было имени

Курс собирал обвязку по частям. Сведём её в карту через три вопроса.

**Что агент знает:**

- `AGENTS.md` — постоянные правила проекта ([этап 5](05-rules-and-memory.md));
- `project/docs/`, ТЗ, ERD — контекст проекта ([этап 4](04-project-context.md));
- skill `db-schema` — карта схемы, чтобы не выдумывать поля ([этап 11](11-skills-and-workflows.md));
- файлы любых форматов: `.docx`, `.csv`, логи, скриншоты ([этап 9](09-files-and-data.md)).

**Что агент может:**

- инструменты: терминал, файловая система, MCP-серверы ([этап 10](10-mcp-tools.md));
- регламенты работы: skills и commands ([этап 11](11-skills-and-workflows.md));
- разделение труда: субагенты `planner`, `worker`, `reviewer`, `tester` ([этап 12](12-subagents.md)).

**Чего агент не может и как это проверяется:**

- права allow/ask/deny, read-only коннект, `.cursorignore` ([этап 13](13-security.md));
- ревью: встроенный `/security-review` и собственный `reviewer` ([этап 8](08-quality-control.md)).

Тринадцать этапов — это и есть harness engineering, просто мы не называли его так. Сегодня достраиваем то, чего в карте не хватает.

## Лестница: prompt → context → harness

Anthropic формулирует первый переход прямо: context engineering — это «естественное продолжение prompt engineering» ([Effective context engineering for AI agents](https://www.anthropic.com/engineering/effective-context-engineering-for-ai-agents), сентябрь 2025). Промпт отвечает на вопрос «что модель должна сделать», контекст — «что модель должна знать».

Третью ступень достроило сообщество в 2026-м: harness отвечает на вопрос «за счёт чего агент **надёжно доводит** работу до конца». Честная оговорка: это удобная дидактическая модель, а не канон вендора. Ступени не вытесняют друг друга — harness включает в себя и промпт, и контекст.

## Слой 1. Guardrails: правило против гарантии

Правило в `AGENTS.md` — это **просьба**. Модель недетерминирована, и чем длиннее контекст, тем меньше веса у ранних ограничений. Guardrail — это **гарантия**: проверка вне модели, которую нельзя обойти уговорами в чате.

Разница ровно та же, что у нас в базе: комментарий `-- не удаляй эту строку` в SQL-файле против `CHECK`-ограничения. Первое — пожелание, второе — не даст записать.

Базовую проверку собираем сами: она кросс-инструментальная и переживёт смену редактора.

`make test` и `make db-audit` возвращают ненулевой код при провале — на этом всё и держится.

**git pre-commit hook** — не даёт закоммитить, пока проверки красные. Держим его в версионируемой папке `.githooks/`, а не в `.git/hooks/`: последняя не попадает в git, и у коллеги этой проверки просто не будет.

```bash
#!/bin/bash
# .githooks/pre-commit
# 1. из коммита не удаляют файл окружения
if git diff --cached --diff-filter=D --name-only | grep -q '^\.env'; then
    echo "нельзя удалять файл окружения — коммит заблокирован"; exit 1
fi
# 2. тесты зелёные
cd "$(git rev-parse --show-toplevel)/project" || exit 1
make test || { echo "тесты красные — коммит заблокирован"; exit 1; }
```

Включается один раз, для всей команды: `git config core.hooksPath .githooks`. Осознанный обход — `git commit --no-verify`.

Агент **не может уговорить hook**. Можно сколько угодно писать «закоммить, тесты потом» — hook остановит. В этом вся разница между правилом и guardrail.

Поверх базового слоя — вендорные механизмы. Принцип один, синтаксис разный:

**Cursor hooks** ([документация](https://cursor.com/ru/docs/hooks)) — конфиг `.cursor/hooks.json`. Хук цепляется к моменту работы агента: начало и конец сессии, перед командой в терминале, перед чтением файла, после правки файла, завершение цикла агента. Правило запоминания: *хотите что-то сделать в определённый момент работы агента — это хук*.

Хуки бывают двух типов, и разница между ними — это ровно разница между просьбой и гарантией:

- **prompt-хук** — вы пишете условие на человеческом языке, его оценивает быстрая модель и возвращает `{ok, reason}`: `{"type": "prompt", "prompt": "Does this command look safe to execute? Only allow read-only operations."}`. Быстро, без кода — но это снова вероятностное решение;
- **command-хук** — вы даёте путь к скрипту, скрипт получает JSON на stdin и печатает решение. Детерминированно.

Три события, которые окупаются сразу:

- `beforeShellExecution` — получает поле `command`, возвращает `{"permission": "allow" | "ask" | "deny"}` плюс `agent_message` (объяснение уходит агенту, чтобы он попробовал иначе). Так закрывается запись в БД: читать можно, менять — только миграцией;
- `beforeReadFile` — блокирует отправку чувствительного файла в модель;
- `stop` — срабатывает, когда агент завершил цикл. Заблокировать его нельзя, но можно вернуть `followup_message`, и Cursor отправит этот текст агенту как следующее сообщение пользователя. Так проверяется «менял `project/` — обнови `task_logs.md`». Ограничитель `loop_limit` (по умолчанию 5, у нас в `hooks.json` стоит 1) не даёт хуку и агенту зациклиться, накручивая токены.

Три честные детали. Коды возврата: `0` — читать JSON, `2` — блокировать, **любой другой — hook считается упавшим, и действие проходит** (fail-open); для защитных хуков ставьте `"failClosed": true`. Хук на терминал закрывает только терминал: агент, которому запретили удалить файл командой, спокойно удалит его инструментом правки файлов. И фильтр ловит ровно то, что вы описали: наш `guard-db.sh` ищет строку `telecom.db` в тексте команды, поэтому `make db-reset`, которая пересобирает ту же базу, пройдёт мимо него.

У других инструментов то же самое, другой синтаксис: **Claude Code** — `PreToolUse` в `.claude/settings.json` с `permissionDecision: "deny"`; **Codex** — sandbox (`read-only`, `workspace-write`, `danger-full-access`) плюс approval policy (`untrusted`, `on-request`, `never`).

Порядок сборки: сначала git/make, потом вендорные hooks как надстройка. Не наоборот — `hooks.json` живёт в конфиге редактора и исчезает при переезде, а git-hook стоит на пути у всех.

## Слой 2. Петля обратной связи

`make db-audit` работает двумя лицами. Для нас это проверка. **Для агента это глаза.**

Без петли агент пишет код вслепую: сгенерировал, отдал, ушёл. С петлёй он запускает проверку, читает вывод, чинит и запускает снова — и останавливается на зелёном. Anthropic прямо пишет, что доступ к инструментам проверки резко поднял качество работы агента, потому что он находил баги, «не очевидные из одного лишь кода» ([Effective harnesses for long-running agents](https://www.anthropic.com/engineering/effective-harnesses-for-long-running-agents), ноябрь 2025).

Чтобы проверка годилась в петлю, она должна быть:

- **машиночитаемой** — агент понимает, что именно упало, без вашего пересказа (наш `audit_db.py` печатает `[FAIL] active-services-on-inactive-sims: 2 row(s)` и сами строки);
- **с ненулевым кодом возврата** — иначе агент не отличит успех от провала;
- **быстрой** — петля из десятиминутных прогонов не петля.

Это и есть максимум пользы для разработчика БД: агент не просто пишет SQL, а сам гоняет `make db-audit`, видит нарушение целостности и чинит данные.

### Ловушка петли: зелёное, но подделанное

У петли есть обратная сторона. Агент оптимизирует **критерий**, а не задачу. Сломан инвариант «активные услуги на неактивной SIM»? Есть два способа получить зелёный аудит: вернуть SIM в статус `active` — или удалить строки услуг из `sim_card_services`. Второй тоже зеленеет, только данные потеряны.

Отсюда — правила петли:

- агенту запрещено менять сами тесты, запросы целостности и критерий;
- финальный `git diff` смотрит человек или независимый `reviewer` ([этап 12](12-subagents.md)).

Подробно про автономные циклы и reward hacking — на [этапе 15](15-team-and-production.md).

## Инструменты harness для БД

Доступ к базе — самый полезный и самый опасный инструмент агента. Правила доступа мы разобрали на [этапе 13](13-security.md): read-only по умолчанию, dev-дамп вместо прода, обратимые миграции. Здесь — чем именно подключать, по росту автоматизации:

1. **Документированная команда** — `make db-check`, `make db-audit`. Скучно, зато прозрачно и версионируется.
2. **MCP-сервер БД** — агент получает базу как полноценный инструмент ([этап 10](10-mcp-tools.md)). Здесь три ловушки, которые надо знать:
   - reference-серверы Anthropic для Postgres и SQLite **архивированы** — в них нашли SQL-инъекцию, обходившую read-only, и npm-пакет так и остался непропатченным. Ставить их нельзя, хотя качают их до сих пор;
   - у живых серверов read-only часто **не является режимом по умолчанию**: у `postgres-mcp` (Crystal DBA) нужно явно указать `--access-mode=restricted`, у Supabase MCP — флаг `--read-only`;
   - Oracle SQLcl MCP (SQLcl 25.2+) read-only обеспечивает привилегиями подключения и пишет все выполненные SQL в лог `DBTOOLS$MCP_LOG` — наблюдаемость, которой стоит требовать от любого доступа агента к базе.
3. **Локальный Oracle XE** как dev-песочница вместо доступа к рабочей базе — путь для тех, кто на Oracle.

На учебном проекте показываем `make`-команды и read-only коннект к SQLite; MCP-сервер и Oracle XE — путь для вашей реальной базы.

## Harness — переносимый актив

Обвязка ценна, только если её легко перенести. Всё держим в git: `AGENTS.md`, `.cursor/skills`, `.cursor/agents`, `.cursor/commands`, `.cursor/hooks.json` со скриптами и `.githooks/pre-commit`. Последний включается у коллеги одной командой `git config core.hooksPath .githooks`. В Claude Code это можно собрать в **plugin** — один устанавливаемый пакет команд, субагентов, skills и hooks для всей команды.

Оговорка, чтобы не было иллюзий: модели пост-тренируют под конкретную обвязку, поэтому перенос модели в чужой harness не бесплатен. Но правила, схема и проверки вашего проекта переезжают вместе с репозиторием — и работают на любой агент, который в него зайдёт.

## Границы: сколько harness нужно

В индустрии идёт живой спор, и честнее показать обе стороны.

За обвязку: Addy Osmani ([Agent Harness Engineering](https://www.oreilly.com/radar/agent-harness-engineering/), O'Reilly, май 2026) утверждает, что «приличная модель с отличной обвязкой бьёт отличную модель с плохой обвязкой». Самый чистый факт в пользу этого — LangChain подняли свой агент с тридцатого места до пятого на Terminal-Bench 2.0, **поменяв только harness**, без смены модели.

Против: исследователи METR не нашли превосходства Claude Code и Codex над простым скаффолдингом, а Борис Черни, автор Claude Code, говорит прямо: «весь секретный соус — в модели». Ставка на то, что рост reasoning-моделей съест значительную часть обвязки.

Аккуратная формулировка, которая переживёт обе стороны спора: **harness определяет, насколько близко вы подходите к потолку модели.** Он не делает слабую модель сильной — он не даёт сильной модели работать вслепую. И он не отменяет финальную проверку человеком.

## Демо на проекте

1. Попросить агента «прибраться в корне» — он удалит `.env.example`. Попытка коммита упирается в pre-commit hook: «нельзя удалять файл окружения». Затем уговорить агента закоммитить без тестов — hook снова не пускает.
2. Сломать инвариант в данных (`UPDATE sim_cards SET status='blocked' WHERE id=1`), показать красный `make db-audit`, отдать вывод агенту и дать ему починить данные. Проверить `git diff`: чинил данные или удалил проверку.
3. Показать `.cursor/hooks/guard-db.sh` на `beforeShellExecution`: `DELETE FROM` по `telecom.db` не выполняется вообще, `SELECT` проходит. И `check-task-log.sh` на `stop`: агент забыл журнал — хук возвращает его к работе через `followup_message`.

## Итог

Harness — это инженерная разница между «иногда срабатывает» и «работает стабильно». Два слоя, которых не хватало курсу: **guardrails** — гарантия вне модели, которую нельзя уговорить, и **петля обратной связи** — машиночитаемая проверка, по которой агент сам доводит работу до зелёного. Модель меняется раз в полгода. Harness остаётся вашим активом.
