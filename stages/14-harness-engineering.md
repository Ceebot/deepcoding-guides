# Этап 14. Harness Engineering

[← К roadmap](../README.md)

Цель: превратить правила-советы в **обвязку**, которая физически не даёт агенту сделать плохо и даёт ему безопасно дотянуться до данных.

## Агент = Модель + Harness

Модель — это «мозг», но качество работы определяет **harness** — всё, что вокруг неё: правила, команды проверки, инструменты, доступы, гейты, контекст. Сильная модель в пустом окружении ведёт себя как стажёр без регламента. Слабая модель в хорошем harness — как стажёр с чек-листами и автотестами: ошибётся реже и заметнее. Сложная и ценная часть — именно harness, и собирать его — инженерная работа.

Базу harness мы уже собрали по ходу курса: правила ([этап 5](05-rules-and-memory.md)), контекст ([этап 9](09-files-and-data.md)), MCP ([этап 10](10-mcp-tools.md)), skills и commands ([этап 11](11-skills-and-workflows.md)), субагенты ([этап 12](12-subagents.md)), безопасность ([этап 13](13-security.md)). Полную лесенку не пересказываем — этот этап достраивает **два недостающих слоя**: детерминированные guardrails и безопасный доступ агента к БД.

## Слой 1. Детерминированные guardrails

Правило в `AGENTS.md` — это **просьба**. Агент может её забыть, особенно когда контекст забит. Guardrail — это **гарантия**: проверка вне модели, которую нельзя обойти уговорами в чате.

Базовый, кросс-инструментальный приём (работает в любом редакторе и у любой модели) — гейт на уровне git и make. Соберём его сами:

- **Makefile-цель `ci`** — один вход для всех проверок. В проекте уже есть `test` и `db-audit`, осталось свести их в одну цель:

```make
ci: test db-audit   # добавьте в project/Makefile; при желании — линтер (ruff и т.п.)
```

- **git pre-commit hook** — не даёт закоммитить, пока `make ci` красный. Репозиторий курса один (в корне), проект — в `project/`, поэтому hook ставится в корневой `.git/hooks`:

```bash
# .git/hooks/pre-commit
cd project && make ci || { echo "проверки красные — коммит заблокирован"; exit 1; }
```

- **CI** — та же `make ci` на стороне репозитория.

Ключевая мысль: агент **не может уговорить hook**. Можно сколько угодно писать «закоммить, тесты потом» — гейт всё равно остановит. Это и есть разница между правилом и guardrail.

Поверх базового слоя — вендорные механизмы, один принцип, разный синтаксис:

- **Claude Code** — hooks в `settings.json` (события жизненного цикла, блокировка на отправке команды);
- **Cursor** — hooks: скрипты на события агента, могут блокировать команду или вычистить секрет;
- **Codex** — sandbox + approval policy.

Сначала ставьте кросс-инструментальный гейт (git/make) — он переживёт смену редактора. Вендорные hooks добавляйте как надстройку.

## Слой 2. Безопасный доступ агента к БД

Самая большая польза агента для разработчика БД — когда он **сам ходит в базу**: разбирает схему, считает отчёт, находит нарушения целостности, объясняет данные. Но это же и самый опасный доступ ([этап 13](13-security.md)). Harness — это то, что превращает рискованный доступ в полезный и безопасный.

Как дать агенту глаза и руки в БД:

1. **Контекст схемы — через skill, а не «угадай».** У нас это `db-schema`: агент видит таблицы, статусы, инварианты и не выдумывает поля. Для реальной БД — тот же приём: один skill с картой схемы.
2. **Права — read-only по умолчанию** ([этап 13](13-security.md)): для анализа и отчётов агенту нужно только чтение.
3. **Чем именно подключать** (это и есть новый слой) — по росту автоматизации:
   - документированный способ: команда/скрипт «подключись к dev-БД и выполни запрос» — у нас это `make db-check` и `make db-audit`;
   - **MCP-сервер базы данных** — агент получает БД как полноценный инструмент ([этап 10](10-mcp-tools.md)), с правами, которые задаёте вы (только чтение, только dev-схема);
   - для тех, кто на Oracle, — локальный **Oracle XE** как dev-песочница вместо доступа к рабочей базе.
4. **Запись — отдельно и обратимо:** только по dev-дампу и только миграцией с откатом.

На учебном проекте доступ показываем через `make`-команды и read-only коннект к SQLite; MCP-сервер БД и Oracle XE — путь для вашей реальной базы, без живого демо здесь.

Связка щёлкает: **доступ** (MCP/`make`) + **контекст** (skill `db-schema`) + **права** (guardrails) + **проверка** (`reviewer`). Агент из «угадывателя SQL» становится аналитиком БД, которому можно доверить отчёт.

## Слой 3. Упаковка harness для переноса

Harness ценен, только если его легко перенести: всё держим в git — `AGENTS.md` ([этап 5](05-rules-and-memory.md)) как кросс-инструментальный файл правил, папки `.cursor/skills`, `.cursor/agents`, `.cursor/commands` и гейты рядом с проектом. В Claude Code это можно собрать в **plugin** — один устанавливаемый пакет команд, субагентов и hooks для всей команды.

## Демо на проекте

1. Собрать цель `ci` (`test` + `db-audit`) и pre-commit hook в корневом `.git/hooks` (`cd project && make ci`). Попросить агента «закоммить без тестов» — показать, что гейт не пускает.
2. Подключить агента к `data/telecom.db` в read-only и попросить **отчёт**: выручка по услугам и активные SIM по клиентам (`project/queries/reports/`). Показать, что агент опирается на skill `db-schema` и не выдумывает поля.
3. Запустить `make db-audit` руками агента — проверка целостности как часть обвязки (читает данные, не меняет их).

## Итог

Harness — это инженерная разница между «иногда срабатывает» и «работает стабильно». Новые слои поверх курса: **детерминированные guardrails** (гейт, который нельзя уговорить) и **безопасный доступ к БД** (read-only + MCP/skill + reviewer). Модель меняется раз в полгода — harness остаётся вашим активом.

- Дать агенту read-only доступ к учебной БД и получить от него готовый отчёт по `project/queries/reports/`.
- Свести правила/команды/субагентов проекта в одну версионируемую папку (или plugin) и описать в `AGENTS.md`, как ими пользоваться.
