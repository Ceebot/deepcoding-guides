# Этап 12. Субагенты и параллельная работа

[← К roadmap](../README.md)

Цель: делить сложную задачу между специализированными агентами — у каждого своя роль и свой чистый контекст, а главный агент ими дирижирует.

## Зачем это нужно

Субагенты для нас не новинка: на [этапе 8](08-quality-control.md) мы своими руками сделали `reviewer` и `tester`, а на [этапе 11](11-skills-and-workflows.md) видели, как `superpowers` под задачу поднимает собственных субагентов. Здесь разбираем механику целиком.

Проблема, которую они решают, — **один агент в одном чате**. Большая задача целиком в одном окне упирается в две стены:

- **Предел контекста.** Окно конечно и меньше, чем кажется: например, в Codex модель держит порядка 256 тыс. токенов. Для правки хватит, для большого исследования или целого блока задач — нет. Окно забивается выводом тестов, простынями файлов, тупиковыми попытками; правила из начала чата «тонут», агент теряет фокус.
- **Замыленный глаз.** Агент, который писал код, его же и проверяет — и своих багов не видит, для него они «так и задумано».

Это «агент-оркестр»: один за всех в захламлённом чате. На мелочи прокатит, на большой задаче рассыпается.

## Что такое субагент

Отдельный экземпляр агента с тремя свойствами:

- **своя роль** — отдельный системный промпт и фокус;
- **своё чистое контекстное окно**, изолированное от главного чата;
- возвращает наверх **только результат**, а не весь черновик.

Главный агент при этом — **оркестратор**: раздаёт задачи и собирает ответы. Ключевой механизм — **изоляция контекста**: субагент-исследователь прочитал тридцать файлов у себя и вернул выжимку на полстраницы, а главное окно осталось чистым. Вместо одного забитого окна — много чистых плюс одно сводящее, и предел контекста перестаёт быть стеной.

Аналогия: вы тимлид. Вы не читаете весь архив сами — сотрудник разбирается за своим столом и кладёт вам страницу выводов, а не ворох черновиков.

## Субагент — это не скилл

У субагента тот же frontmatter, что у скилла (`name`, `description`), и работает он похоже: эти два поля всегда висят в контексте (постепенное раскрытие), по ним агент решает, кого позвать, и **может вызвать субагента автоматически** — по совпадению описания с задачей. Деятельная фраза в описании («Use proactively для ревью…») — прямой сигнал к авто-вызову. Полный промпт роли грузится только при вызове, поэтому субагентов можно держать хоть десяток.

Но назначение разное:

```bash
.cursor/skills/   # инструкция «как делать» — подмешивается в текущего агента
.cursor/agents/   # отдельный исполнитель со своим окном — ему делегируют работу
```

Скилл встраивается в текущего агента, субагент — отдельный исполнитель. В Claude Code — `.claude/skills/` против `.claude/agents/`.

## Роли субагентов

- **Planner** — изучает задачу и делает план.
- **Explorer** — исследует проект.
- **Worker** — реализует код.
- **Tester** — пишет и запускает тесты.
- **Reviewer** — ищет баги.
- **Security** — проверяет секреты, инъекции, доступы.
- **Docs** — обновляет документацию и журнал.

Это **не обязательный стандарт**, который надо выписывать в файлы: чаще всего такие роли уже встроены в зрелые инструменты и агентные системы и вызываются сами.

## Создаём субагента и выбираем модель

Руками писать необязательно — в Cursor есть `/create-subagent`. Опишите имя, роль, контекст, задачи и ограничения:

```md
/create-subagent
Имя: planner
Роль: планировщик задач проекта Telecom SIM Cards.
Контекст: project/, SQLite + Python + pytest, ТЗ telecom-sim-cards-spec.md.
Задачи: декомпозировать задачу на шаги, оценить риски, сохранить план в .cursor/plans/.
Ограничения: код не меняет, только планирует.
```

При создании можно **выбрать модель** (в файле — поле `model`). Это рычаг экономии:

- на **планирование и ревью** — мощная модель: цена ошибки высокая;
- на **реализацию по готовому плану** — модель попроще, заточенная под код.

Умная голова придумала план, дешёвая реализовала — экономим токены, не теряя в качестве.

## Руками или готовое

Личное мнение: вручную прописывать целый штат (planner/worker/tester/reviewer) сегодня чаще всего **избыточно** — современные агенты сами назначают роли и поднимают субагентов, а под оркестрацию есть готовые навыки `superpowers`: `dispatching-parallel-agents` (несколько независимых агентов параллельно) и `subagent-driven-development` (фича по плану силами субагентов).

Ценность ручного субагента — **не в роли** (планировщики и ревьюеры есть в любом готовом наборе), а в **зашитом знании проекта**. Пример — ревью миграции. Готовый ревьюер проверит стиль SQL и инъекции, но не знает правил, которые живут только в вашем ТЗ:

- статус SIM меняется только по цепочке `available → reserved → active → blocked/lost`;
- миграции идемпотентны и обратимы;
- `price_at_connection` фиксируется в момент подключения и не пересчитывается;
- активная SIM без единой услуги — нарушение, а не норма.

Готовый ревьюер пропустит ломающую миграцию как валидный SQL — а ваш собственный `reviewer` с этими инвариантами поймает.

Правило: хватает общих знаний о ремесле — берите готового или встроенного; нужны схема, инварианты и договорённости проекта — пишите руками.

## Связка скилл + субагенты

Skill может не просто давать регламент одному агенту, а описывать **порядок вызова субагентов**. Пример — `.cursor/skills/subagent-workflow/SKILL.md`: цепочка с циклом.

```
Задача → planner → worker → tester → reviewer → [замечания?] → worker (цикл) | завершено
```

Каждый субагент запускается в своём контексте, оркестратор передаёт handoff (путь к плану, список файлов, `git diff`, блок замечаний). Ценность — **цикл до чистого ревью**: задача доводится до конца, а не бросается на первом «вроде готово». Вызов — один промпт:

```md
Используй skill .cursor/skills/subagent-workflow/SKILL.md.
Задача: выполнить <блок задач из todo.md> через planner → worker → tester → reviewer
с циклом до чистого ревью.
```

## Когда запускать параллельно

- **Разведка** нескольких частей проекта — по субагенту на кусок.
- **Несколько вариантов решения** — сравнить и выбрать (каждый worker пишет в свою ветку/папку).
- **Сравнить ответы разных моделей.**
- **Независимое ревью в несколько глаз** — нашли двое-трое независимо → реальный баг, а не вкусовщина.

```md
Запусти параллельно трёх explorer'ов:
1) опиши схему таблиц SIM-карт и статусы;
2) найди миграции, затрагивающие sim_cards;
3) собери тесты по SIM-картам.
Собери ответы в один короткий обзор.
```

## Большой аудит — связка всего курса

Показательный кейс для разработчиков БД: огромный проект — сотни SQL-файлов, гора миграций, скрипты за годы. Аудит **всего** в одном окне невозможен (помните предел 256 тыс. токенов — схема и миграции туда не влезут). Решение: оркестратор нарезает базу на части и пускает по субагенту на каждую параллельно, потом сшивает выжимки в переиспользуемый skill — карту БД, как `db-schema`, только сгенерированную по реальному коду.

```md
Проведи аудит SQL-кодовой базы силами субагентов.
1. Раздели код на части: схемы/DDL, миграции, запросы, скрипты.
2. На каждую — отдельный субагент-аудитор в своём контексте: таблицы, связи,
   ограничения, индексы, узкие места. Для поиска по файлам — fff.
3. Собери ответы и оформи как skill .cursor/skills/db-overview/SKILL.md.
Только чтение, код не меняй.
```

Тут лесенка курса щёлкает в один механизм: **fff** ([этап 10](10-mcp-tools.md)) ищет, **субагенты** делят нагрузку, итог упаковывается в **skill** ([этап 11](11-skills-and-workflows.md)) и дальше подмешивается во все будущие задачи.

## Когда контекст кончается

Приём на каждый день, даже без субагентов. Видите, что окно заполняется, — не воюйте с ним, **переезжайте в новый чат**, но сначала снимите саммари сессии в файл:

```md
Контекст почти заполнен. Напиши в docs/handoff.md краткое саммари этой сессии:
что сделано, какие решения приняты, что осталось и где остановились.
Без воды — чтобы новый чат продолжил ровно с этого места.
```

Открываете чистый чат, даёте ему этот файл — продолжаете с памятью, но без мусора. Тот же принцип изоляции контекста, только вручную.

## Контроль и безопасность

В духе deepcoding:

- **Не дробите всё подряд.** Для правки на две строки команда из пяти агентов — из пушки по воробьям. Параллельные субагенты множат расход токенов.
- **Осторожно с параллельной записью.** Агенты друг друга не видят: писать параллельно — только в изолированные ветки или папки, иначе затрут работу друг друга.
- **Результат субагента — всё ещё «грязный код»** (Zero Trust, [этап 8](08-quality-control.md)). Делегируете работу, но не ответственность: финальный diff проверяете вы.
- **Без доступа к production и секретам** без явной необходимости.

## Итог

Лесенка инфраструктуры, которую мы строили весь курс:

- **rules** (этап 5) — постоянные правила;
- **контекст** (этап 9) — файлы любых форматов;
- **MCP** (этап 10) — руки и глаза;
- **skills и commands** (этап 11) — по какому регламенту работать;
- **субагенты** (сегодня) — между кем разделить работу.

ИИ-команда ускоряет, а роли, границы и финальную проверку задаёт инженер.

## Домашнее задание

- Одну задачу поручить двум агентам параллельно: один планирует, другой ищет похожий код.
- Сравнить результаты.
- На основе двух ответов составить финальный план.
- Для смелых: собрать связку скилл + субагенты (`planner → worker → reviewer`) и прогнать через неё одну реальную задачу с циклом до чистого ревью.
