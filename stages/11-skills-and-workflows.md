# Этап 11. Skills, commands и reusable workflows

[← К roadmap](../README.md)

Цель: перестать печатать один и тот же длинный промпт. Вынести повторяющийся регламент в файл, который агент подключает сам, когда задача подходит.

## Зачем это нужно

MCP с прошлого этапа отвечал на вопрос «куда агенту сходить» — к доке, в браузер, к базе. Skills отвечают на другой: «по какому регламенту он действует». Это последний слой инфраструктуры: правила, контекст и инструменты мы уже собрали, осталось задать сам порядок работы.

Вот промпт, который иначе печатаешь руками каждый раз, когда что-то добавляешь в проект:

```md
Изучи ТЗ project/telecom-sim-cards-spec.md и свежий task_logs.md.
Найди похожие миграции, seed и SQL в project/.
Составь короткий план, не меняй лишнего, меняй только project/.
После правок прогони make db-clean db-migrate db-seed.
Обнови task_logs.md.
Задача: ...
```

А вот то же самое одной строкой — весь регламент уже зашит внутри:

```md
/sim-feature
Задача: ...
```

Правило простое: если вы напечатали один и тот же длинный промпт три раза — это уже не промпт, а инструкция, и её пора вынести в файл.

## rule, skill, command — три разные вещи

Их часто путают:

- **Rule** — постоянное правило проекта (этап 5): «отвечай по-русски», «не трогай production», «после изменений в `project/` обновляй `task_logs.md`». Живёт в `AGENTS.md`, `CLAUDE.md` или `.cursor/rules` и **подмешивается в контекст всегда**.
- **Skill** — навык под конкретный тип задачи. Главное отличие от правила: подключается, **когда задача подходит**, а не висит в контексте постоянно.
- **Command** — короткая кнопка запуска: `/review`, `/reset-db`, `/sim-feature`.

Коротко: rule — правила поведения сотрудника, skill — инструкция на конкретную работу, command — кнопка запуска этой работы.

## Где это лежит

```bash
AGENTS.md, .cursor/rules    # rule — базовые правила проекта
.cursor/skills/             # skills — навыки под задачи
.cursor/commands/           # commands — кнопки быстрого запуска
.cursor/agents/             # субагенты-ревьюер и тестировщик (этап 8)
```

Skills понимают разные инструменты, и у каждого своя папка: Cursor смотрит в `.cursor/skills/`, Claude Code — в `.claude/skills/`, остальные — в переносимый стандарт `.agents/skills/`. У каждого skill своя папка, внутри — `SKILL.md`.

Если команда работает сразу в нескольких инструментах, копировать одни и те же скиллы в три места — плохая идея: это как держать один метод в пяти местах проекта, легко запутаться в поддержке. Решение — **один источник и симлинки**: реальные файлы лежат в одной папке, остальные на неё ссылаются.

```bash
.agents/skills/                      # оригинал — настоящие папки скиллов
.claude/skills -> ../.agents/skills  # симлинк: Claude видит те же файлы
```

Команду помнить необязательно — попросите агента:

```md
Сделай так, чтобы Claude видел скиллы из .agents:
симлинк .claude/skills → ../.agents/skills
```

## Проектные и глобальные скиллы

- **Проектные** лежат в репозитории (`.cursor/skills`, `.agents/skills`). Заточены под этот проект, едут вместе с ним в git, достаются всей команде.
- **Пользовательские (глобальные)** лежат в домашней папке (`~/.agents/skills`, `~/.claude/skills`). Доступны во **всех** проектах — это ваш личный инструментарий, не привязанный к репозиторию: например `generate-commit`, `create-transcription`.

Удобный приём: сделать `~/.agents/skills` симлинком на папку в облаке (Google Drive) — тогда личные скиллы синхронизируются между всеми вашими машинами и руками ничего копировать не надо.

## Из чего состоит skill

Skill — это не только «пошаговый процесс». Есть три применения:

- **процедура** — строгий порядок шагов (`sim-card-feature-workflow`);
- **мелкая рутина** — одно действие, которое легко забыть (`update-task-log`);
- **знание** — упакованный контекст, который агент подтягивает по надобности (`db-schema`: карта БД, статусы SIM-карт, CHECK-ограничения — чтобы перед SQL не выдумывать поля).

По стандарту skill — это папка, и внутри может быть больше, чем `SKILL.md`:

```
sim-card-feature-workflow/
├── SKILL.md      # обязательный: frontmatter (name, description) + инструкция
├── scripts/      # исполняемый код, который агент запускает (run-checks.sh)
├── references/   # доки, читаются только по надобности (sql-conventions.md)
└── assets/       # шаблоны и заготовки (business-check.sql)
```

Ключевая идея деления — **постепенное раскрытие контекста**. Skill грузится в несколько стадий:

1. всегда в контексте висят только `name` и `description` каждого скилла — чтобы агент знал, когда скилл вообще нужен;
2. понял, что нужен — читает целиком `SKILL.md`;
3. по ходу работы запускает `scripts/` и подтягивает `references/` и `assets/`.

Поэтому скиллов можно держать хоть сотню: постоянно в контексте — только пара строк названий и описаний, тяжёлые файлы грузятся по требованию.

Это **открытый стандарт**, не фишка одного редактора. Формат `SKILL.md` придумали в Anthropic и отдали в открытый доступ — его понимают Cursor, Claude Code, Gemini CLI и десятки других инструментов. Витрина: [agentskills.io](https://agentskills.io).

## Создаём и вызываем skill

Skill необязательно писать руками — можно попросить агента. Но не «создай хороший skill», а дать реальные повторяющиеся действия, ограничения и критерий успеха:

```md
Создай skill .cursor/skills/db-smoke/SKILL.md.
Назначение: быстрая проверка учебной БД после пересборки.
Skill должен требовать:
- SELECT count(*) по таблицам clients, sim_cards, services, payments;
- вывести результат одной таблицей;
- ничего не менять в данных и схеме.
```

Вызов готового скилла — короткий промпт, весь регламент уже внутри:

```md
Используй skill .cursor/skills/db-smoke/SKILL.md.
```

Ремарка: в некоторых сборках есть готовая команда `/create-skill` или навык `writing-skills` из superpowers — они делают то же по более строгому шаблону. Нет такой команды — обычный промпт выше работает не хуже.

## Commands — кнопки для частых действий

Технически команда — это просто markdown-файл в `.cursor/commands/`. Имя файла становится именем команды, содержимое — текстом, который подставляется в чат по слэшу. Никакого кода — обычный промпт, который надоело печатать. Команды бывают от одной строки до целой процедуры:

```md
# use-context7.md — микро-директива
use context7 mcp

# reset-db.md — ярлык рутины
1. make db-clean
2. make db-migrate
3. make db-seed

# sim-feature.md — запуск скилла
Используй skill .cursor/skills/sim-card-feature-workflow/SKILL.md.
Сначала покажи план и список файлов. Без изменений до подтверждения.
Задача:
```

Особенно выручает в команде: новому разработчику не надо помнить, как у вас принято пересобирать базу или готовить релиз — он жмёт команду, и агент получает правильный стартовый контекст.

## superpowers — универсальная библиотека рядом с вашей

`superpowers` (этап 10) — **не MCP**, а плагин с готовыми инженерными регламентами. Разница с вашими скиллами:

- ваши `.cursor/skills` — **локальная** библиотека под проект (`sim-card-feature`, `db-schema`): знают про SIM-карты и вашу схему;
- superpowers — **универсальная** библиотека «как инженерить вообще»: брейншторм, системная отладка, TDD, ревью. Не знает ваш проект, зато знает ремесло.

Обе прекрасно работают рядом. Минус честно: superpowers тратит много токенов — большой контекст, вопросы, иногда субагенты. Для правки на две строки избыточно; для большой фичи, сложного бага или рискованной задачи — самое то.

## Когда делать skill

Делать стоит, если:

- вы повторили один и тот же промпт больше двух раз;
- у задачи строгий порядок шагов.

Не стоит — если это разовая мысль на две строки, иначе разведёте мусорную библиотеку, где агенту труднее найти нужное.

Итог-лесенка, которую мы строили несколько этапов:

- **rules** (этап 5) — постоянные правила;
- **контекст** (этап 9) — кормим агента файлами любых форматов;
- **MCP** (этап 10) — даём руки и глаза;
- **skills и workflows** (сегодня) — задаём, как именно агент работает.

Польза не в красивой структуре папок, а в том, что повторяющаяся рутина из головы разработчика превратилась в исполняемый регламент — от обновления `task_logs.md` до безопасного деплоя. Это и есть deepcoding: ИИ ускоряет работу, а порядок, границы и контроль задаёт инженер.

## Домашнее задание

1. Найдите у себя один повторяющийся workflow.
2. Напишите для него `SKILL.md` в `.cursor/skills/<name>/` (или в переносимый `.agents/skills/<name>/`).
3. Прогоните через него одну реальную задачу.
4. После прогона сократите skill: уберите воду, добавьте забытые ограничения.

Хороший skill рождается не с первого раза — он дозревает после пары реальных задач, когда видно, где агент ошибается и что надо зафиксировать явно.
